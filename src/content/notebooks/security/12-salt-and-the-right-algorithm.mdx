```text
  salt = 16+ random bytes, UNIQUE PER USER, stored next to the hash
         (it is not a secret. it does not need to be.)

  stored:  argon2id$v=19$m=65536,t=3,p=4$<salt>$<hash>
                                          ▲      ▲
                                          │      └ hash(password + salt)
                                          └ different for every single user
```

The salt does one job and does it completely: <Peach>identical passwords now produce
different hashes</Peach>, so a precomputed table is worthless and every password must
be attacked individually.

| Algorithm | Verdict |
|---|---|
| MD5, SHA-1, SHA-256 | <Rose>Never for passwords.</Rose> Fast is the wrong property |
| PBKDF2 | Acceptable, widely certified, weakest of the three below |
| bcrypt | <Peach>Fine.</Peach> Long-established. Note the 72-byte input limit |
| scrypt | Good. Memory-hard |
| <Peach>argon2id</Peach> | The current default recommendation. Memory-hard and side-channel resistant |

<DoThis>

What to actually do

- <Mint>Use the library's defaults</Mint> for argon2id or bcrypt and do not invent
  parameters. Raise the work factor over time as hardware improves.
- <Mint>Let the library generate the salt</Mint> and store it in the encoded hash
  string. Never write your own salt handling.
- <Mint>Never write your own comparison.</Mint> Use `verify()`, which is
  constant-time; `==` on hash strings leaks timing.
- <Mint>Set a maximum password length</Mint> (say 1,024 characters) so nobody can make
  you argon2 a 10 MB body. Denial of service by hashing is real.
- <Mint>Do not impose composition rules</Mint> ("one symbol, one capital"). Length and
  a breached-password check (Have I Been Pwned's k-anonymity API) beat
  character classes, which mostly produce `Password1!`.

</DoThis>

<Ask>

What is peppering, and do you need it?

A <Pink>pepper</Pink> is a secret value mixed into the hash that lives in your
application config or an HSM rather than the database. It means a stolen
<Peach>database alone</Peach> is not enough to attack the hashes offline. It is genuinely
useful, and the cost is that rotating it requires rehashing on next login and
that losing it locks everyone out. Reasonable to describe as "a defence-in-depth
option I would consider, not a substitute for a slow salted hash".

</Ask>
