| You cannot | Because |
|---|---|
| Modify an object in place | Objects are <Pink>immutable</Pink>; you replace the whole thing |
| `seek()` and overwrite bytes 4,000 to 4,004 | No partial write. Download, edit, re-upload the whole object |
| Have real folders | Keys are flat strings; hierarchy is an illusion (section 14) |
| Rename | Copy to the new key, delete the old. Costs the <Peach>full size</Peach> of the object |
| Lock a file | There is no lock. There is now a conditional write (section 22) |
| Expect microseconds | Every operation is an <Peach>HTTP request over a network</Peach>: milliseconds to tens of milliseconds |

#### What you get

- <Peach>Nothing to coordinate.</Peach> No in-place mutation means no distributed locking
  protocol, no write ordering to agree on, and an entire category of distributed
  systems problems simply does not arise.
- <Peach>No tree.</Peach> No directory structure to maintain, lock, split or rebalance. A
  flat key space partitions trivially.
- <Peach>Any node can serve any request.</Peach> Each operation is a self-contained,
  authenticated HTTP request, so a fleet of stateless front-end nodes scales
  horizontally without limit.
- <Peach>No capacity planning.</Peach> Nothing to provision, nothing to resize.
- <Peach>Durability as a product.</Peach> 11 nines from the provider, section 19.
- <Peach>Directly addressable over HTTP.</Peach> Browsers, mobile apps, video players, curl,
  a CDN: anything that speaks HTTP can talk to an object without going through
  your server at all. This is what makes presigned URLs possible, and it is the
  single most important consequence of the whole design.
