Authentication on a WebSocket has one awkward constraint and one architectural
problem, and neither is obvious until you hit them.

**The constraint: the browser cannot set headers.** `new WebSocket(url)` takes a
URL and an optional subprotocol list, and no headers. <Peach>You cannot send
`Authorization: Bearer`</Peach>, exactly as with `EventSource` in section 10. Three
options:

| Approach | The problem with it |
|---|---|
| **Cookie** | Sent automatically at the handshake. <Peach>Enables the attack in section 39</Peach>, and needs `SameSite` |
| **Token in the query string** | <Rose>Lands in access logs, proxy logs and browser history</Rose> |
| **<Mint>Authenticate in the first message</Mint>** | Connection is open but unauthenticated for a moment; you must enforce a deadline |

<Mint>The practical answer is a short-lived, single-use ticket</Mint>, fetched from an
ordinary authenticated endpoint and passed in the query string. It leaks into
logs, but a single-use credential with a 30-second life is not worth stealing.

```text
  POST /realtime/ticket   ──▶ { "ticket": "rt_9f3...", "expires_in": 30 }
  new WebSocket("wss://api.example.com/ws?ticket=rt_9f3...")
   ──▶ server redeems it, once, and binds the connection to the user
```

<Mint>Do not stop here.</Mint> The harder half of the problem is what happens to that
authentication over the next four hours, which is the next section.

<KeyIdea>

Browsers cannot set headers on a socket, so the credential goes in the URL.
<Peach>Use a short-lived, single-use ticket</Peach> rather than a real token, so what lands
in your access logs is worthless by the time anyone reads it.

</KeyIdea>
