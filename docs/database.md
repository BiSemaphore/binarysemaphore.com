# The database

The schema, and why it has the shape it has. The SQL in `supabase/migrations/`
is the source of truth and carries the detail; this file carries the decisions,
including the ones that were considered and rejected.

## How we got here

The first ten migrations grew by accretion, each answering the question in front
of it. The result had four problems that were not opinions:

- **Three of ten migrations were content edits** (`0004`, `0005`, `0009`). The
  folder was turning into a changelog of content decisions written in SQL.
- **The notebook catalog had two sources of truth.** Eleven rows in
  `learn_products`, the same eleven in `src/lib/learn.ts`, titles duplicated,
  nothing checking they agreed.
- **A surrogate key nobody used.** `entitlements` carried `id uuid primary key`
  next to `unique (user_id, product_id)`. Production index statistics settled
  it: the primary key had been scanned **2** times, the unique constraint
  **223**. `reading_progress`, written later, already used a composite key. The
  two tables disagreed about their own design.
- **Closed sets stored as unconstrained text.** A typo in `status` wrote a row
  that silently never matched `status = 'active'` again, and a reader lost
  access with no error anywhere.

Production held about 75 rows of exploratory data, so it was rebuilt rather than
reshaped. The old migrations are gone and the set starts again.

## Why not MongoDB

Asked and answered, so it does not get re-litigated.

Our data is relational in the way relational databases exist for: a channel
belongs to a subject, an entitlement joins a user to a notebook, a revision
points at a document. Supabase's auth lives in Postgres, so every per-user table
hangs off `auth.users` by foreign key. In Atlas that join stops being enforceable
by the database and becomes something the application remembers to do.

The larger loss is RLS. The access boundary currently sits inside the database,
so a bug in a route handler cannot leak another reader's rows. Atlas has no
equivalent, and the boundary would move entirely into Node. With admin writes
arriving, that is a downgrade.

A second database is also a second backup story, a second migration story, a
second set of credentials, and no transaction spanning the two.

It would earn its place with schemaless per-tenant blobs, high-volume event
writes, or Atlas Search over millions of documents. We have hundreds of
documents and one writer.

## The one idea

**We do not have three kinds of content. We have one.** A thread, a topic
channel and a notebook section are each a slug, a title, MDX, and a publish
state. They differ in what surrounds them, not in what they are.

So: one `documents` table, plus a thin satellite per kind. That collapses three
editors, three revision tables, three publish workflows and three search indexes
into one of each.

The failure mode this avoids is the _other_ version of the same idea: one wide
table with nullable columns per kind. There, `subject` has to be nullable
because threads have no subject, and "every channel has a subject" becomes a
rule enforced in TypeScript and therefore eventually not enforced. On a
satellite it is `not null`.

Roadmaps stay in `roadmaps.ts`. Structured data, one editor, no reason to move.

## The decisions worth knowing

**Slugs are a domain, not a text column.**

```sql
create domain public.slug as text
  check (value ~ '^[a-z0-9]+(-[a-z0-9]+)*$' and length(value) between 1 and 80);
```

Slugs are URLs. One line makes a broken link impossible rather than unlikely, in
one place instead of in every policy.

**Slugs are unique within a scope, not globally.** Java has a channel called
`interview-questions` and so will half the other subjects. `documents.scope` is
the container a slug is unique within: the subject for a channel, the notebook
for a section, null for a thread. A thread's null must collide with another
thread's null, hence `unique nulls not distinct (collection, scope, slug)`,
which needs Postgres 15 or later. The remote runs 17, and `config.toml` now
says 17 too, where it had drifted to 15.

**`scope` and the satellite's foreign key must agree**, and no SQL constraint
expresses "this column equals that column in another table". A single generic
trigger does, named by argument, so the invariant lives in the database rather
than in the one write path somebody later forgets.

**A published document cannot be empty.**

```sql
constraint published_has_a_body
  check (status <> 'published' or (body_mdx is not null and published_at is not null))
```

This is what makes an admin panel safe. A blank page cannot reach the site by
accident, because the database will not hold one.

**`origin` prevents silent data loss.** Notebook sections are generated by
`scripts/sync-notebooks.mjs` from the `learnings` repo. Without a marker saying
a script owns the row, an admin edits a section and the next sync overwrites the
edit with no trace. `origin` is `admin` or `sync`, and the editor refuses to
open a `sync` row.

**Revisions are written by a trigger, not by application code**, because a
trigger cannot be forgotten by the one code path that skipped it. Revision N
stores what the page looked like _before_ save N. This is the rollback that
leaving git costs us.

**Ordering is a plain integer with no unique constraint**, read as
`order by (position, title)`. At 23 subjects and 93 channels, fractional or
gap-based ordering is machinery maintained for no reason. Revisit above a few
thousand rows.

**`body_mdx` is not a separate table.** Postgres moves large text out of line
automatically, so a listing that does not select it does not pay for it. A
separate body table would buy only an extra join.

## Two schemas

| Schema    | Holds                                          | Has a URL |
| --------- | ---------------------------------------------- | --------- |
| `public`  | content the world may read, rows a reader owns | yes       |
| `private` | the admin list, revisions, the inbox           | **no**    |

`config.toml` exposes only `public` and `graphql_public` to PostgREST, so
nothing in `private` is reachable over HTTP at all. Server code uses the service
key; the admin uses `security definer` functions that check `is_admin()` first.
RLS remains the boundary. This removes the surface that would otherwise exist
purely because `public` is the default.

## Authorisation

Two rules, neither negotiable.

**RLS filters rows; it does not grant table access.** Both a `grant` and a
policy are required. Forgetting the grant is what produced "permission denied
for table entitlements" the first time round.

**Being able to sign in must never imply being an admin.** "Allow new users to
sign up" is a global switch, not per provider, and the email provider is
enabled, so anyone in the world can obtain an account on this project. That has
to stay true, because a student signing in with Google is a signup. The gate is
a row in `private.admins`, checked by `is_admin()`.

`private.admins` has no client write path in any schema under any role short of
the service key. An admin cannot promote anyone, including themselves. It
carries a `role` column (`admin` or `editor`) which costs one column now and
saves a migration the first time someone should be able to write prose without
being able to change the tree.

The subdomain is routing, not security. `binarysemaphore.com/admin` reaches the
same route tree, and `parseHost()` returns a null root for an unrecognised host
which the proxy deliberately leaves alone, so a Vercel preview URL serves
`/admin` with no subdomain check at all. None of that matters while the boundary
is RLS.

## Content is not a migration

Migrations hold schema and nothing else. Content moves through a sync script
that is idempotent and re-runnable and leaves no permanent SQL file per typo.

It runs **once, in one direction**: git to Postgres. After that the MDX files
are deleted and Postgres is the source of truth. Two-way sync, or leaving both
live and editable, is how content is silently lost.

## Deliberately not built

- **A `profiles` table.** `auth.users` already holds the email. A copy is a
  second thing to keep in step and a second thing to leak.
- **A general audit log.** `document_revisions` covers the thing that needs
  history. An audit table nobody reads is a table nobody maintains.
- **Fractional ordering, tags as a table, i18n, comments, workflow states beyond
  draft/published/archived.** None have a caller.
- **`note_requests` folded into the inbox.** It looks like inbox mail and is
  not: the reader has to read their own row back so the button can say "you
  asked for this" rather than inviting the same person to ask five times. The
  inbox is admin-only.

## What this costs

Every thread and channel page becomes a query plus an MDX compile where today it
is a compiled import, so `unstable_cache` with tags is not optional
(`cacheComponents` is not enabled, so `use cache` does not apply). Build-time
MDX errors become runtime errors, mitigated by compiling on save and refusing to
store what does not compile. Review of copy on a preview deploy goes away, which
is what `document_revisions` buys back.

## Verified, not assumed

The set was applied to the real database inside a transaction that was rolled
back, and the invariants were exercised rather than read. All seven held:

| Check                                                        | Result                                  |
| ------------------------------------------------------------ | --------------------------------------- |
| A published document must have a body                        | rejected as designed                    |
| The `slug` domain rejects `Not A Slug`                       | rejected as designed                    |
| Two threads cannot share a slug, though both scopes are null | rejected as designed                    |
| The same slug is allowed in two different subjects           | accepted, which is the point of `scope` |
| A satellite cannot disagree with its document's `scope`      | rejected by the trigger                 |
| An edit writes a revision automatically                      | one row                                 |
| The revision holds the title from _before_ the save          | confirmed                               |

Plus the inbox path end to end: `record_inbox_message` writes a row that keeps
its `context`, starts as `new`, and is callable by `service_role` alone. `anon`
and `authenticated` have neither execute on the function nor usage on the
schema.

Worth repeating whenever a policy or constraint changes. Wrapping the whole set
in `begin; ... rollback;` works because Postgres DDL is transactional, so it is
a real test rather than a syntax check.

## Applying it

The migration set has been validated against the real database inside a
transaction that was rolled back, so the SQL and its dependency order are known
good. It is **not applied**, and it must not be applied on its own:
`grant_learn_access`, `has_learn_access` and `product_id` are referenced by
shipped application code, so pushing the schema without the matching code change
breaks the live notebook reader.

Schema and code land together, in this order:

1. Push the schema to a branch database or accept a short window.
2. Update `src/lib/learn/` for `notebooks`, `notebook_id`, and the renamed
   access functions.
3. Seed the catalog and the topic tree with the sync script.
4. Then the admin, per `docs/admin.md`.
